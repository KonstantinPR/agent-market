# Agent Market

Веб-приложение для анализа прибыльности продаж на маркетплейсах
(Wildberries и Ozon). FastAPI + PostgreSQL + pandas; Excel-импорт/экспорт,
расчёт маржинальности, панельные выгрузки из API и кнопка массового обновления.

В панелях «WB API» / «OZON API» у кнопок «Скачать Excel» есть галочка
«в БД» (запоминается в браузере): снята — данные скачиваются в Excel без
записи в базу (не влияет на кнопки «Обновить WB / Ozon», они всегда пишут).

## Автопилот цен Wildberries

Раздел «Прибыльность ▸ Автопилот цен WB» рассчитывает целевую скидку по
каждому товару и опционально применяет её через WB API (`upload/task`,
меняется только скидка, базовая цена карточки не трогается).

- Правила R1-R10: остатки/DOC, скорость продаж и тренд (momentum),
  конверсия воронки и кол-во «в корзине», пена возвратов/отмен,
  докупаемость товара, мёртвый запас, перезапас, кулдаун между применениями.
- Цена никогда не опускается ниже порога убытка: unit-экономика берётся из
  продаж (комиссия, логистика, хранение, услуги, себестоимость), маржа-пол —
  настройка `floor_margin_pct`.
- Рост цены (уменьшение скидки) — только при реальных продажах; докупаемые
  товары (флаг «Докупаемый» в разделе «Товары») поднимаются умеренно.
- Параметры двигателя редактируются на странице (сохраняются в браузере);
  дефолты — `app/services/pricing.py`. Журнал решений — в таблице `price_changes`
  (страница «Журнал решений»). Для миграции существующей БД выполнен
  `scripts/init_db.py` (идемпотентно добавляет колонку `replenishable`).

Сейчас изменения в Wildberries через API **не вносятся**: кнопка
«Экспорт в Excel» сохраняет рекомендации (целевые скидки, решения, причины)
в `pricing_<дата>.xlsx`; применение через `upload/task` (эндпоинт
`POST /api/pricing/apply`) будет включено после добавления токена
`WB_API_KEY` с правом «Цены и скидки».

## Карточки товара маркетплейса (marketplace_cards)

«WB API ▸ Карточки товара» хранит **сырые** карточки Wildberries как есть:
одна строка — размер/SKU (`marketplace_cards`): `chrt_id`, артикул продавца,
артикул WB, размер, баркод, объём (л.), состав, бренд, предмет, название.
В будущем в ту же таблицу пишутся карточки Ozon и других маркетплейсов
(разделитель — `marketplace_id`).

- **Загрузка из Excel** (поле для файлов/перетаскивание): один `.xlsx`,
  несколько файлов или zip-архив с Excel-файлами (`POST /api/import/cards`).
  Заголовки распознаются как из выгрузки ЛК WB (Бренд, Предмет,
  Код размера (chrt_id), Артикул продавца, Артикул WB, Размер, Баркод,
  Объем, л., Состав), так и из API WB (`chrtId`, `vendorCode`, `nmID`,
  `techSize`, `barcodes`, `title`).
- **Загрузка из API** (`POST /api/wb/cards`) пишет те же строки дополнительно
  к общему каталогу.
- Общий каталог «Наш склад ▸ Товары» (`products`) автоматически обновляется
  из карточек: новые артикулы добавляются, существующие обновляются
  (наименование, бренд, баркод). Карта `nmID → артикул` (`nm_articles`) — тоже.
- После каждой загрузки строка «Последняя загрузка» показывает время, число
  строк, записанных карточек и (для Excel) количество файлов.

## Потребность в товаре: выгрузка в PDF

Раздел «Наш склад ▸ Потребность в товаре» умеет отдавать не только Excel, но и
PDF для печати/закупки — с фотографиями товара.

- Кнопка «Экспорт ▸ PDF ▸» в тулбаре раздела: галочки полей (те же, что у
  таблицы), число фото на карточку (0–9) и галочка «с фото».
- Фото берутся с локального диска, путь — `PHOTOS_ROOT` в `.env`
  (по умолчанию `C:\YandexDisk\ФОТОГРАФИИ`). Имена файлов грязные
  (`— копия`, `(2)`, `.JPG.JPG`, файлы без номера), приоритет у активной папки,
  `АРХИВ` используется только если активной нет. Совпадение артикула — без
  учёта регистра; при несовпадении артикула продавца и папки есть аккуратный
  fallback по укороченному префиксу (покрытие ≈ 80 %).
- Товары без фото всё равно попадают в отчёт — просто без картинки.
- Формат: A4 книжная, один блок на товар, до 9 фото (1 крупное + остальные
  столбиком), строки размеров с итогом, общий итог в конце, колонтитул с
  датами и страницей.
- Миниатюры кэшируются в `data/thumbs/` (папка не коммитится), индекс фото
  держится в памяти 10 минут — повторная выгрузка не читает диск заново.
- Ограничение: не больше 500 позиций за раз (по умолчанию 100). Если список
  обрезан, в ответе есть заголовок `X-Truncated`, а в интерфейсе — подсказка
  о числе пропущенных позиций.

## Запуск

```powershell
venv\Scripts\python.exe app\main.py   # http://127.0.0.1:8000
```

Перед первым запуском выполнить `scripts/setup_pg.*` (создание БД) и
`scripts/load_sample.py` (демо-данные). Ключи API — в `.env` (см. `.env.example`
при наличии). `.env` в git не коммитится.

## Разработка

### Git (только локальный)

```powershell
git init
git add -A
git commit -m "Initial commit"
```

Ветка `main`, история хранится локально. В `.gitignore` исключены
`.env`, `venv/`, `data/`, `.pytest_cache/`, `.coverage`, `htmlcov/`, `*.log`.

Работа идёт через тикеты (`TICKETS.md`): номер выдаёт git-ветка
`t-<N>-<слаг>`, а подробности — в [docs/](docs/). Проверка перед коммитом:

```powershell
venv\Scripts\python.exe -m app.services.tickets validate   # exit 1 = проблемы
venv\Scripts\python.exe -m app.services.tickets report     # сводка по задачам
```

### Тесты

Тесты пишутся в отдельную БД `<PG_DATABASE>` (по умолчанию
`agent_market_test`), рабочая БД не затрагивается. База создаётся
автоматически при первом запуске; постгрес-пользователь из `.env` должен
иметь право `CREATE DATABASE`.

```powershell
venv\Scripts\python.exe -m pip install -r requirements-dev.txt
venv\Scripts\python.exe -m pytest                    # все тесты
venv\Scripts\python.exe -m pytest tests\unit -v      # unit
venv\Scripts\python.exe -m pytest tests\api -v       # API (TestClient + тестовая БД)
venv\Scripts\python.exe -m pytest tests\e2e -v       # сквозной сценарий (маркер e2e)
venv\Scripts\python.exe -m pytest --cov=app          # с покрытием
```

Структура:

- `tests/unit/` — чистые юнит-тесты (формулы, нормализация, планы, ошибки);
- `tests/api/` — HTTP-эндпоинты и фоновые задания обновления;
- `tests/e2e/` — сквозной цикл «панели + массовое обновление»;
- `tests/js/` — проверка `app/static/app.js` через `node --check` и Node `vm`.

Провайдеры маркетплейсов в тестах заменяются фейками (`tests/fakes.py`)
через единую точку `app/providers/factory.py`; реальные HTTP-вызовы не
выполняются. Координаты тестовой БД подменяются в `tests/conftest.py`
(переменная окружения `PG_DATABASE`).

### Проверка перед коммитом

```powershell
venv\Scripts\python.exe -m py_compile app\*.py app\services\*.py app\providers\*.py
node --check app\static\app.js
venv\Scripts\python.exe -m pytest
```

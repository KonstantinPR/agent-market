# Проект agent_market

Локальный агрегатор маркетплейсов Wildberries / Ozon: панель статистики продаж,
маржинальности, остатков, карточек, прайсов. Backend FastAPI (app/), фронтенд —
статические файлы (app/static/), БД PostgreSQL.

```
│   │                       (factory.py — подмена на фейки в тестах,
│   │                        errors.py — нормализованные ошибки)
│   ├── services/           бизнес-логика — ЕДИНСТВЕННОЕ место расчётов
│   └── static/             фронтенд: index.html, app.js, style.css
├── scripts/                init_db.py (схема+миграции), load_sample.py,
│                           gen_api_map.py (docs/api.md + таблица размеров)

├── docs/                   architecture.md, api.md, autopilot.md, research-*.md
├── data/                   thumbs/, кэш — в git не коммитится
├── TICKETS.md              очередь задач
├── AGENTS.md               этот файл — точка входа для агента
└── README.md               запуск и описание продукта
```

Ориентиры внутри `app/services/` (полная таблица со строками — в
`docs/architecture.md`): `sync.py` — запись выгрузок WB/Ozon в БД;
`refresh.py` — `pull_*` и кнопки «Обновить WB / Ozon»; `margin.py` —
маржинальность; `replenish.py` — подсортировка/потребность; `pricing.py` —
автопилот цен; `common.py` — общие хелперы (wildcard-фильтр `like_*`);
`tickets.py` — реестр тикетов.

Куда класть новое коротко: расчёты → `app/services/<фича>.py`; HTTP к
маркетплейсу → `app/providers/`; эндпоинт → хвост `app/api.py`; вкладка/таблица
→ `app/static/index.html` + `app/static/app.js` (см. «UI таблиц»); колонка БД →
идемпотентный `ALTER ... IF NOT EXISTS` в `scripts/init_db.py`.

## Кодировка (UTF-8, без BOM)

Все текстовые файлы проекта — UTF-8 **без BOM**. PowerShell 5.1 по умолчанию
читает их как системную ANSI (cp1251), поэтому round-trip
`Get-Content | Set-Content` (и `-Encoding UTF8`, который кладёт BOM)
безвозвратно портит кириллицу: «Меню» → «Р,єРµРЅ», в начало файла
подмешивается `EF BB BF`.

- **Не читать/не писать** файлы проекта через `Get-Content`/`Set-Content`/
  `Out-File`. Править инструментами редактирования или Python
  (`open(path, encoding="utf-8")`), без BOM.
- Скрипт-заменители (например правка `?v=` в `index.html`) — тоже на Python,
  не через PowerShell-`replace`.
- Проверить после правки: в первых байтах нет `EF BB BF`, кириллица читается
  (`Get-Content -Encoding Byte -TotalCount 3` → нет 239/187/191).
- Если mojibake уже попал в файл — обратимо: прочитать как UTF-8, каждый
  символ с `ord ≤ 0xFF` заменить на байт `cp1251`, результат декодировать
  как UTF-8 и записать без BOM.
- Учтено в тестах: `tests/js/test_js_helpers.py` и `scripts/gen_api_map.py`
  читают исходники явно с `encoding="utf-8"`.

## Тикеты

Единая очередь задач проекта — файл `TICKETS.md` в корне репо.

- Перед началом любой разработки прочитать `TICKETS.md`.
- Работа идёт через тикеты, но необязательно: взять открытый тикет с наивысшим
  приоритетом → завести ветку `t-<N>-<слаг>` → перевести в «В работе» →
  код + тесты → коммит `feat|fix(область): описание` → перенести тикет
  в «Закрытые» с хешем коммита.
- Номер тикета выдаёт git, а не файл: `git switch -c t-<N>-<слаг>`, затем
  `tickets.create(..., branch=...)` — метка `T-<N>` подставится из имени ветки.
  Ветка `main` для новой работы не используется. Создание без ветки (кнопка в
  веб-вкладке) берёт max+1 и годится только когда никто параллельно не заводит
  тикет.
- Тело тикета — до трёх строк (`где` / `состояние` / `нужно`). Разборы и логика
  живут в сообщении коммита или в `docs/`.
- Если тикету нужны внешние данные/доступ (токен, доступ «Статистика»,
  решение владельца) → «Заблокированные» + описание ожидания.
- В «В работе» одновременно может быть несколько тикетов.
- Тикеты ведутся через вкладку «Тикеты» в веб-приложении (кнопки
  «Добавить/Взять в работу/Закрыть») или правкой `TICKETS.md` — оба
  способа работают с одним файлом.
- Проверка целостности файла: `python -m app.services.tickets validate`
  (exit 1 = есть проблемы). Ловит метку в двух разделах, пометку не по разделу и
  тикет в «В работе» без ветки (агент не начал или потерял работу). Те же
  проверки гоняет `tests/unit/test_tickets.py::test_repo_tickets_md_is_valid` —
  «зелёный» прогон обязателен перед коммитом.
- Сводка по состоянию проекта: `python -m app.services.tickets report`.
- Правки `TICKETS.md` делать по структуре (раздел/метка), а не по подстроке
  `replace('Название раздела', ...)`: заголовки разделов в файле встречаются
  ровно один раз, а переименование раздела «поверх» недопустимо — номер тикета
  не переиспользуется никогда.
- Если задача поступила устно («добавь тикет: …») — оформить её в файл
  и работать по нему же.

## Фотографии товара (T-31)

- Источник — папка с фото на диске, путь в `.env`: `PHOTOS_ROOT`
  (по умолчанию `C:\YandexDisk\ФОТОГРАФИИ`, ~60 500 файлов / 137 ГБ). Папка
  **не входит в git**; настройки в `app/config.py` (`photos_root`,
  `thumbs_dir`, `thumb_max_px=800`, `thumb_quality=82`).
- Имена файлов на диске грязные, поэтому разбор в `app/services/photos.py`:
  артикул = часть до последнего `-<число>`, номер фото = это число; из имени
  вырезаются `— копия`, `copy`, `(2)`, двойные расширения (`.JPG.JPG`); файл
  без номера считается первым фото своего артикула. Сравнение артикулов —
  без учёта регистра.
- Выбор папки: активная важнее `АРХИВ` (регистронезависимо, в любом сегменте
  пути), затем папка с большим числом фото, затем имя папки. Номера фото
  сортируются числом, не именем.
- Артикул на диске не всегда совпадает с артикулом продавца (бывает `SH016-…`
  против `SK016-…`), поэтому есть fallback по укороченному префиксу
  (`PREFIX_FALLBACK`, только для ключей ≥ `MIN_PREFIX_LEN`, и только при
  ровно одном совпадении). На живых данных покрытие ≈ 80,5 %.
- Индекс кэшируется в памяти (`ttl=600 c`), полный обход диска не выполняется
  на каждый запрос. Миниатюры кэшируются на диске в `data/thumbs/` (в git
  не коммитится); ключ кэша учитывает путь + mtime + размер + параметры.
- Выгрузка: `GET /api/export/replenish/pdf`, меню «PDF ▾» в разделе
  «Потребность в товаре» (внутри — галочки настроек и кнопка «Скачать PDF»;
  отдельной кнопки в тулбаре нет, она бы дублировала и «протухала» бы при
  смене дат без «Применить»). **Поля карточки = колонки «Вида таблицы» вида
  «По артикулам»** (отдельного списка галочек в меню больше нет — дублировал
  «Вид таблицы»; `replenishPdfCols()` читает `colViewState("replenish",
  "article")`, режим задаётся явно, потому что PDF всегда по артикулам).
  Служебный ключ таблицы `status` бэкенд мапит на `status_label`
  (`_REPLENISH_COL_ALIASES`, тот же аллиас работает и для Excel) — иначе
  «Статус» в PDF/Excel не печатался вовсе. Фото: `photo_count` по умолчанию
  **6** (селектор 1…`PDF_MAX_PHOTOS=9`), товары без фото не выбрасываются,
  а печатаются без картинок. `limit` 1..500 (по умолчанию
  100) и `X-Truncated` предупреждают, что список обрезан.
- Колонка «Продано WB, шт» (вид «По артикулам», ключ `wb_sells`) — **нетто**:
  продажи WB минус возвраты за окно, поэтому «Продано WB ÷ дни окна» = «WB, шт/д».
  В разрезе «По размерам» `wb_sells` — гросс (без вычета возвратов, а `wb_vel`
  там считается от нетто): известное расхождение одного и того же ключа между
  видами, «чинить» только вместе с владельцем.
- Вид «По размерам» показывает **все размеры карточки WB** (каталог размеров
  `ProductSize` в базе пуст, размеры берутся из `MarketplaceCard.size`), включая
  «везде 0» — те, что в окне не продавались и не лежат ни на одном МП
  (штрихкод тогда из карточки). Чекбокс «без нулевых размеров» тулбара
  (`hide_zero_sizes=1`, по умолчанию снят) отсекает такие размеры — это тот же
  фильтр, что в `wb_sorting_plan` называют «мёртвыми». Параметр едет и во
  выгрузку Excel (`/api/export/replenish`), PDF он не касается (там своя логика
  карточек).
- Правила сортировки WB в PDF (`replenish.wb_sorting_plan`, действуют и на экране):
  **пустой размер без продаж получает 1 шт** (`WB_SORT_MIN_SIZE_STOCK`, чтобы размер
  вообще отображался на карточке WB) и **окно скорости** выбирается селектором
  «Скорость по:» 180 / 365 дней / всё время (`vel_days=0` — от первой продажи артикула;
  делится на фактический span окна, а не на запрошенные дни). Если короткое окно
  не видит продаж — скорость 0, но правило «1 шт» всё равно закладывает штуку.
- **«Дослать» и «WB дефицит» в таблице (оба вида) = итог `wb_sorting_plan`**
  с параметрами PDF по умолчанию (`_wb_sort_plan`: скорость 180 дн, пол 1 шт,
  прибыльность). Раньше экран считал дефицит по окну фильтра, и в окне без
  WB-продаж пустая карточка показывала 0, хотя PDF планировал дослать штуку.
  Теперь значения идут из плана (колонка «Дослать`, ключ `to_sort`, в Excel
  «Дослать на WB, шт» — в обеих картах `_REPLENISH_EXPORT`/`_REPLENISH_EXPORT_SIZES`),
  а «Отгрузить WB» покрывает этот дефицит с нашего склада. Для артикулов/размеров
  без данных WB остаётся прежний расчёт по окну спроса. Стоимость: план считает
  маржу за 180 дн и WB-скорость — таблица стала тяжелее ≈ на PDF-расчёт.
- **Учёт прибыльности** (галка в меню «PDF ▾», по умолчанию включена, `profit=0/1`):
  покрытие = выбранный период ÷ 4 (`PROFIT_MARGIN_DAYS=365` окно маржи, а не скорости),
  а целевой уровень домножается на `profit_factor = min(2.0, 2·rent% / 30)` —
  линейно от 0 при ≤0 % рентабельности до ×2.0 при 30 % и выше. Коэффициент один
  на артикул (себестоимости по размерам нет) и печатается в карточке
  («учёт прибыльности: подсорт ×N»). Убыточные (коэффициент 0) и полностью
  закрытые товары в PDF не попадают — они идут в `X-Truncated`. Источник маржи —
  тот же `margin.margin_detail_dataframe`, что и колонки «Маржа/шт»/«Рентабельность».
  `profit=0` — старый режим: покрытие из поля «Запас», без коэффициента.
- Замер (RX 6600, живые данные): PDF с прибыльностью 3.7 с (180 дн) / 7.3 с (365 дн)
  / 9.3 с (всё время), без галки — 1.7 с.
- **PDF из Excel-файла с правками** (T-37): в меню «PDF ▾» есть дропзона —
  перетащить отредактированную выгрузку «Потребность» (кнопка «Excel»). Файл —
  источник истины: состав карточек и значения печатаются из него, отбраковка
  убыточных/полных не применяется, фильтры таблицы игнорируются. Разбор —
  `app/services/excel_import.py` (`POST /api/replenish/import-excel`): колонки по
  русским подписям из `_REPLENISH_EXPORT`, дубли распознаются (в т.ч. `Метка.1`
  — pandas переименовывает повторы), строки без артикула отбрасываются и
  считаются, лимит `MAX_ROWS=5000`; `POST /api/export/replenish/pdf` грузит
  `{rows, source}` и собирает тот же PDF. Бюджет «Итого дослать» по артикулу —
  колонка «WB дефицит» (`replenish.apply_sort_budget`): пустая ячейка = расчёт
  по складу; заданный бюджет распределяется по размерам (vel desc, круговой
  добор продающимся), сумма размеров = бюджет. Приписка « · из Excel: имя»
  в футере; футер умеет ужиматься до двух строк — до T-37 длинная строка
  футера молча уезжала за край страницы (drawString не переносит).
- **Не объединять `UPPER(article) IN … OR UPPER(barcode) IN …` в один запрос** в
  `margin.margin_detail_dataframe`: Postgres по OR не применяет индекс (Seq Scan +
  сравнение с массивом 16k элементов = 9 с на окне 365 дней), а два раздельных
  запроса дают тот же набор строк за 0.2 с (проверено на живых данных 7384 == 7384).
- Шрифты PDF: Windows-пути (`segoeui.ttf`, `arial.ttf`) с откатом на
  reportlab-шрифты. Кириллица в PDF проверена тестами — не «лечить» кодировку
  текста вручную.

## Тесты

- Код в `tests/` (unit + api через TestClient), структура и команды — в

- Основная команда: `& "C:\python_projects\agent_market\venv\Scripts\python.exe" -m pytest -q`

- Маркеры: `-m fast` — быстрый прогон без БД/сети (цель < 20 с, для итераций),
  без маркера — весь набор (~2 мин). Полный прогон обязателен перед коммитом.
  `fast` проставляется автоматически в `tests/conftest.py` (тесты в `tests/api`
  и `tests/e2e`, а также любые с фикстурами `db`/`client`, в `fast` не входят) —
  руками не наносить.
- **Защитные тесты-манифесты** (`tests/unit/test_*_manifest*.py`,
  `test_routes_snapshot.py`) читают исходники статически и ловят «забыл
  добавить место» ещё до запуска:
  - `test_tab_manifest.py` — навигация ↔ секции ↔ `loadTabInner` ↔ «Вид
    таблицы» ↔ `apiPullByTab`;
  - `test_routes_snapshot.py` — снимок всех `/api`-роутов: новый роут →
    вписать строку в `SNAPSHOT` внизу файла (комментарий там же), пропавший
    роут тест поймает сам;
  - `test_column_manifest.py` — ключи колонок «Вид таблицы» (app.js) ↔
    export-словари (api.py): известные расхождения зафиксированы в
    `KNOWN_JS_ONLY`/`KNOWN_PY_ONLY` (после починки запись убирается), новых —
    тест не пропустит. Подписи колонок («Выручка» vs «Выручка, руб») здесь
    не проверяются — они на этапе рефакторинга колонок;
  - `test_local_storage_manifest.py` — ключи localStorage ↔ реестры `LS_KEYS`
    (с описаниями) и `LS_COLVIEW_KEYS` (app.js): новый ключ браузера —
    занести в реестр, иначе тест падает.
- Тестовые данные/фейки — `tests/fakes.py` (мок WB/Ozon API, когда `testing_mode`).
- Фронтенд-линта/typecheck нет; синтаксис JS при необходимости: `node --check app/static/app.js`.
- Общая тестовая БД `agent_market_test`: параллельные прогоны дедлочат —
  гонять полный набор в одиночку.

Все табличные данные выводятся **только** через существующий табличный движок
`pagedTable` / `table` / `totCell` / `applyStickyCols` / `initHeaderTip` в
`app/static/app.js` — **не плодить новые движки таблиц**. Требования ко **всем**
таблицам проекта (нынешним и будущим):

1. **Закреплённый хедер** — шапка таблицы (sticky) всегда видна при вертикальной прокрутке.
2. **Строка итогов** рядом с хедером (липкая под шапкой). Правило значений:
   - **сумма** — для остатков, сумм, дефицитов, отгрузок, «в пути», маржи;
   - **среднее (≈)** — для скоростей (шт/д), дней запаса, долей/процентов, цены за единицу
     («где итог не подходит — среднее»);
   - **пусто** — где итог неосмыслен (артикул, название, статус, штрихкод).
   Реализация: объект `footers` в вызове `pagedTable`; для среднего — `{ avg: n, dp: x }`
   (`dp` — знаков после запятой при кастомном рендере колонки) или `{ avg: n, pct: true }`
   для колонки-процента. См. `replenishFooters` / `replenishSizeFooters`.
3. **Сортировка по клику на заголовок** (числовые — по значению, текстовые — по «ru»-locale).
   Клик по строке заголовка — переключение asc/desc.
4. **Закрепление первого столбца** (`pinned: ["article"]`) — строка/артикул виден при
   горизонтальной прокрутке. Если идентифицирующая колонка не «article» — закреплять её.
5. **Всплывающее пояснение колонки** — у каждой колонки задано `tip`
   («что за поле и как считается»), рендерится через `data-tip` + пузырь `#hdrTip`
   (см. пунктирное подчёркивание заголовка). НЕ ставить нативный `title` на `th`
   со сортировкой — он перебивает подсказку «Сортировать».
6. **Горизонтальный скролл** + нижний скроллбар (`t-xbar`), **сохранение позиции
   прокрутки** при сортировке/перерисовке (не «улетать» в начало).
7. **Пагинация**: «Показано X из Y», «Показывать: N», «Загрузить все (N)».
8. **Панель фильтров** над таблицей (`.toolbar`): поиск по артикулу/названию, период/окно,
   настройки вида. Изменение фильтра перезагружает таблицу (`loadTab`). Обработчики
   писать через общие хелперы `app.js` — не копировать `clearTimeout+setTimeout`:
   `onTabInput(id, tab[, run[, ms]])` — ввод с debounce (по умолчанию 400 мс,
   перезагрузка только пока вкладка активна), `onTabChange(id, tab[, run])` —
   селект/чекбокс сразу, `debounceRun(fn, ms)` — произвольный отложенный запуск.
   Ошибка загрузки вкладки сама попадает в статус шапки (`showLoadError` в
   `catch` у `loadTabInner`) — свой catch с console.error не дублировать.
9. **Выгрузка в Excel**: роут `/api/export/...` + карта колонок (`_EXPORT` в `app/api.py`),
   кнопка в тулбаре.
10. **Пустое состояние** — «Нет данных за выбранный период».
11. Числовые колонки: `num: true` (выравнивание вправо), рендер через общие `cellFmts`
    (`money/pct/int/intZero/...`), а не собственные форматтеры.
12. **Версионирование**: после любого изменения фронтенда бампить `UI_VERSION`
    в `app/static/app.js` и `?v=` у `/static/app.js` в `app/static/index.html`.
13. **Информационная строка-сводка** (параметры вида «Окно: … · Запас: … · Строк: … ·
    срочно: … · нет нигде: …»): показывать в шапке сразу после кнопки «Применить»
    (элемент `.header-msg`), а не внутри панели таблицы. Если строка длиннее
    **150 символов** — обрезать до 150 + «…», полный текст показывать
    всплывающей подсказкой при наведении (тот же `data-tip` + `#hdrTip`).
    На других вкладках строка не остаётся (очищается при уходе со своей вкладки).

Чек-лист при добавлении новой таблицы: `headers` (с `tip` на каждой колонке) →
`footers` (сумма/среднее по правилу п.2) → `pinned` → export-роут → контролы `.toolbar`
→ тесты API → live-проверка → бамп версии. Эталон следования всем правилам —
вкладка «Потребность в товаре» (виды «артикулы» и «размеры»).

### Чек-лист: новая вкладка целиком

Вкладка — это всегда **пять мест в двух файлах**, и без любого из них она
работает молча не до конца. Порядок такой (X — имя вкладки, например `wb-funnel`):

1. **`app/static/index.html`** — `<a class="nav-link" data-tab="X" href="#">`
   в навигации (где положено по разделу: «Наш склад ▸», «WB API ▸», …).
2. **`app/static/index.html`** — `<section id="tab-X" class="pane">` с тулбаром
   (`.toolbar`), кнопками и контейнером таблицы.
3. **`app/static/app.js`**, `loadTabInner` — ветка `else if (name === "X") await renderX(...)`.
   Нет ветки → клик по пункту меню не вызывает ничего (ошибки не будет).
4. **`app/static/app.js`** — функция `renderX()` поверх `pagedTable` + параметры
   из панели фильтров; колонки/`tip`/`footers` — по памятке выше.
5. **`app/static/app.js`** — по необходимости:
   - «Вид таблицы»: три элемента с именами от `ccTab(X)`
     (`btn<CcTab>View`, `<CcTab>ViewMenu`, `<CcTab>ViewPanel`) + `registerColView("X", …)`;
     её `storageKey` — в список `LS_COLVIEW_KEYS` (реестр localStorage, см. ниже);
   - «Обновить базу»: запись в `apiPullByTab`;
   - экспорт: `downloadViewExcel`/`wbViewExportUrl` или своя кнопка → свой `/api/export/…`;
   - фильтры тулбара: `onTabInput`/`onTabChange` (п.8 памятки выше);
   - новое состояние в браузере → ключ в `LS_KEYS` с описанием
     (реестр localStorage; иначе падает `test_local_storage_manifest.py`);
6. **`app/api.py`** — роуты `/api/...` и `/api/export/...`; логика — в `app/services/`.
7. **Бамп версии** (п.12 выше) и тесты из «Перед коммитом».

Проверить, что ничего не забыли, помогают защитные тесты из раздела «Тесты»:
`tests/unit/test_tab_manifest.py` (навигация ↔ секции ↔ `loadTabInner` ↔
«Вид таблицы» ↔ «Обновить базу»), `test_routes_snapshot.py` (роуты не пропали),
`test_column_manifest.py` (колонки панели ↔ export-словари) и
`test_local_storage_manifest.py` (ключи браузера ↔ реестр `LS_KEYS`).

## Примечания

- Реальные ключи WB/Ozon: `app/config.py` (`Settings`, читается из `.env`):
  `wb_api_key`, `wb_finance_api_key`, `wb_finance_api_key_2` (резервный финансовый
  для ротации при 429), `ozon_client_id`, `ozon_api_key`. Ключи в логи не писать.
- Ротация финансовых ключей: `WbProvider._session_post(..., finance=True)` при ответе
  429 делает одну попытку вторым ключом (`WB_FINANCE_API_KEY_2`), затем как раньше.
  Тесты: `tests/unit/test_providers_errors.py` (мок `requests.post`).
- WB «Выкупы»/«Сумма выкупа» в воронке: WB не отдаёт их через текущий токен
  (`statistics-api .../api/v1/main` отвечает 404 — нужен доступ «Статистика»).
  Колонки показывают «—» и заметку; заполнятся после получения доступа и нового скачивания воронки.
- Ручная загрузка «Детализации продаж» WB (Excel/zip): `POST /api/wb/detail-upload`
  (обход лимитов finance-api; файл из ЛК WB).
- Акции WB «Календарь акций» (T-25): другой хост —
  `https://dp-calendar-api.wildberries.ru/api/v1/calendar`, токен `wb_api_key`
  (не финансовый). Лимит 10 req/6 с, всплеск 5 → пауза 0.7 с.
  - `GET /promotions?startDateTime&endDateTime&allPromo=false&limit&offset` →
    `data.promotions[{id,name,startDateTime,endDateTime,type}]` (с пагинацией).
  - `GET /promotions/details` батчами ≤100 promotionIDs → `participationPercentage`,
    `ranging[{condition,participationRate,boost}]`, счётчики `inPromoActionTotal/Leftovers`,
    `notInPromoActionTotal/Leftovers`, `exceptionProductsCount`.
  - `GET /promotions/nomenclatures` и `POST /promotions/upload` к auto-акциям
    неприменимы — отвечают 422.
  - **Per-product «требуемой скидки по акции» WB не отдаёт** (в `products` есть только
    наша `discount`). Поэтому мин/макс-колонки по акциям не выдумываются; связка с
    автопилотом сделана агрегатным правилом R11 (`pricing._promo_pass`) через
    ranging-тиры. Обратная задача («срезать лишнюю скидку при выходе из акции»)
    без per-product данных нерешаема — реализован только добор.
  - Даты WB-акций — с временем и `Z`; БД хранит naive UTC, конверсия `_promo_dt`
    в `app/services/sync.py`.
  - **Семантика лестницы ranging — наша интерпретация, не данные WB.** Условие у
    всех уровней `productsInPromotion`, а `participationPercentage` агрегатный, по
    товарам самой акции. Поэтому уровень участия конкретной строки автопилот
    выводит из ЕЁ скидки (`pricing._promo_pass`, хелпер `tier_metrics`):
    `promo_boost_gain` = буст наивысшего тира с `rate ≤` целевой скидки,
    `promo_gap_pp` = `tier_pct −` целевая скидка (пересчитывается после добора).
    Не выдавать эти числа за то, что WB сообщил о конкретном артикуле.
  - Правило R11 — только добор, плоский (`+promo_push_pct` на первых K кандидатов)
    и только вниз по скидке. Срезание скидки при выходе из акции сознательно не
    реализовано: без per-product требований WB порог среза был бы выдумкой.
    Колонка `promo_delta_discount` отделяет вклад акции от `delta_discount`,
    который остаётся «правила R1-R10 + акция».

## Перед коммитом

Единый чек-лист (он же канонический — README и `docs/architecture.md` сюда

```powershell
# 1. Рабочее дерево: нет ли чужих незакоммиченных правок (см. ниже «Параллельная работа»)
```

  «Закрытые» с хешем.

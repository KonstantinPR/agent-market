# Исследование: анализ прибыльности Ozon без разреза по размерам

Статус: **реализовано** (T-24). Документ описывает и исходный разбор, и итоговое
правило группировки, и то, как оно встроено в отчётность.
Связанные разделы: «Прибыльность ▸ Детализация маржи OZON», «Ozon API ▸ Детализация
продаж», «Ozon API ▸ Размещение (хранение)», «Обзор».

## Проблема

- **Wildberries**: детализация продаж идёт **по артикулам** (без разреза по размерам) — это корректно и удобно.
- **Ozon**: детализация идёт **по артикулоразмерам**. Артикул сделан в формате `основа-размер`,
  где размер — суффикс после **последнего** `-` в артикуле (например `JBG-08283-A12753-29` →
  основа `JBG-08283-A12753`, размер `29`).
- Нужно сравнивать Ozon и WB на одном уровне детализации, то есть считать **по товару**,
  сохранив возможность посмотреть разрез по размерам.
- На сайте Ozon такой режим есть и называется **«Объединён»**: по умолчанию группирует
  товары, отличающиеся только размером.

## Реализованное правило выделения базы

Модуль `app/services/ozon_article.py`, функция `resolve_offer()` — приоритеты:

1. `alias`   — ручное соответствие `product_aliases` (`alias_article` → `article`).
2. `native`  — нативная группировка Ozon («Объединён»), `NATIVE_BASE_COLS`; поле в данных
   **не подтверждено**, см. «Непроверенное» ниже. Код — точка врезки.
3. `wb`      — поиск артикула WB с отбрасыванием хвостовых сегментов. Совпадение на
   **полном** артикуле = товар **безразмерный** (`HAT-05-BLUE-PINK`).
4. `tail`    — хвост из цифр или известный размер (S/M/L/XL…) = размер.
5. `whole`   — иначе товар безразмерный, дефис в конце не трогаем.

### Почему не «просто последний дефис»

На 41 533 карточках Ozon (сентябрь 2026) наивное правило:

- ломает **376** безразмерных товаров (`HAT-05-BLUE-PINK` → база `HAT-05-BLUE`, размер `PINK`);
- ошибается ещё в **505** случаях, где артикул WB заканчивается раньше
  (`JBG-J763-A7871A1-9-23` → база `JBG-J763-A7871A1`, размер `9-23`).

С приоритетами выше расхождение с группировкой WB — **0.36 %** (12 групп из 3 357).

Сырые построчные списки (постинги, начисления, строки детализации) **всегда** остаются по
конкретному `offer_id` — это операции конкретной карточки. Группируются только своды.

## Бэкфилл

`python scripts/backfill_ozon_articles.py` — идемпотентно пересчитывает `base_article`/`size`
во всех накопленных данных. Артикулы берутся не только из карточек, но и из самих таблиц
(`collect_stored_offers`): товар может продаваться/лежать на складе, ещё не попав в
`marketplace_cards`. Без этого такие строки не сворачивались.

Прогон 2026-09-27: **90 821** строк (детализация 168, начисления 241, размещение 22 499,
карточки 41 533, остатки 1 102, цены 25 278, выкупы 0 — таблица пуста).

Не разложены и остаются пустыми 123 строки начислений — это услуги/логистика без
`offer_id` (`bucket='other'`, type 46/76); в UI они идут отдельной строкой «прочие начисления».

## Проверка на боевых данных (2026-09-27)

- «Размещение (хранение)» за 2026-08-01…09-26: **119** строк по товарам против **121** по размерам.
- Детализация маржи/свод: пример `JBG-5868-207A` (по товарам) ↔ `JBG-5868-207A-27` (27).
- Поиск по базовому артикулу находит и свод, и построчные строки.
- Дашборд: KPI Ozon `articles` = 32 (по базам), цены сохраняют наименования,
  у grouped-строк заполнены `sizes_count`/`offers_count`.
- Тесты: `499 passed` (`tests/unit/test_ozon_article.py`, `test_margin`, `test_sync`,
  `test_dashboard`, `test_replenish`, `tests/api`, `tests/js`).

## Непроверенное

- **Нативная группировка Ozon не подтверждена.** На 2026-09-27 Seller API отдаёт `429` на
  `/v2/analytics/stock_on_warehouses`, `/v3/product/info/list` и предполагаемые
  `/v1|v2/product/group/*`; документация недоступна (web search `403`). В карточках, которые
  мы видели, есть только Ozon Product ID, Offer ID, SKU, Barcode и Name — это не доказательство
  отсутствия поля. Если поле найдётся, достаточно добавить его имя в `NATIVE_BASE_COLS`:
  оно станет приоритетом №1 и перестроит группировку без правок отчётности.
- 11 SKU с начислениями не привязываются к товару: `offer_id` пуст, карточек Ozon с таким
  `chrt_id` (SKU) в `marketplace_cards` нет — 0 совпадений. Данные за 2026-09-01…09-28:
  продажи `+21 750`, комиссия `-11 310`, логистика `-2 759`, услуги `-289`, и при этом 1 135
  строк размещения — товары на Ozon есть. В детализации, остатках и выкупах их нет.
  Без карточки `offer_id` неоткуда взять, а `/v3/product/info/list` для запроса по SKU
  отдаёт `429` (см. выше) — ждём снятия лимита.

## Решения по «открытым вопросам» исходного ТЗ

- Правило базы — как в разделе «Реализованное правило»: приоритеты, эвристика только fallback.
- Артикулы без размера — база = артикул как есть.
- Переключатель — в панели фильтров каждого свода (маржа Ozon, детализация, размещение), по
  умолчанию свёрнуто по товарам, состояние у каждого отчёта своё (ключ `ozBySize:<tab>`);
  в режиме «Строками» переключатель приглушен и не действует.
- Правило нужно всем сводным отчётам Ozon (маржа, детализация, размещение, цены, остатки,
  дашборд), кроме «Пополнить» — там разрез по размерам обязателен.
- В grouped-строке есть колонки «Размеров» (`sizes_count`) и «Артикулов» (`offers_count`) —
  информация о развороте не теряется; список размеров доступен через экспорт/поиск по базе.
